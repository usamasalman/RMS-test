Executive Assessment — Is This Plan Realistic?
Verdict:  The plan&apos;s engineering design is sound and correctly sequenced (RBAC and Audit Trail as the shared foundation before everything else). The main risk isn&apos;t the technical design — it&apos;s that the document contains zero effort/time estimates, and it implicitly commits to redoing this scope on top of storage and multi-tenancy assumptions that may not hold. Treat the estimates and sequencing notes below as the missing piece before this plan becomes a committed roadmap item.
1. What the plan gets right
Correct dependency ordering: RBAC (WS2) before Audit Trail (WS1) before everything else is the right call — every other workstream needs to know who did the thing and whether they were allowed to.
The audit entry / snapshot model (field-level diff, immutable log, version counter) is architecturally appropriate for SOC 2 CC7.2/CC8.1 and ISO 27001 A.5.28 — this is the same pattern mature GRC platforms use.
Severity-tiered approval logic (Critical → CRO, High → Compliance, Moderate → Risk Owner) directly answers the client due-diligence gap flagged in the last review (Q7).
Reusing the working Asset Register import pattern for Workstream 8, instead of inventing a new approach, is the right instinct — assuming that pattern is confirmed still functional (see Section 3).
The verification plan (Part 7) gives testable, falsifiable acceptance criteria per workstream — this is genuinely unusual rigor for a prototype-stage codebase and should be preserved as-is.
2. What&apos;s missing: effort, timeline, and capacity reality
The source plan has no hours, days, or weeks anywhere in it — it is a scope document, not a schedule. At constrained part-time hours (the pace used to produce the existing 6-month platform roadmap), 200–260 hours is roughly 2.5–4 months on its own. This workstream cannot be treated as a side task alongside the other Month 2–5 roadmap items (multi-tenancy, AI ingestion, PDPL/NCA ECC mapping, Arabic RTL, billing) without re-sequencing the overall roadmap — it needs to be slotted in explicitly, not assumed to run in parallel for free.
3. The load-bearing assumption that needs re-verification first
Flag:  This plan&apos;s Part 1 “What Actually Works Today” table states the 3-stage scoring pipeline is fully wired server-side and that Asset Register import genuinely reads uploaded files. A prior code audit of this same codebase found the third scoring stage (computePostTreatmentRRS) defined but never called, and — separately — found an upload handler that inserted hardcoded records instead of reading the file. If those findings have since been fixed, good; if this table is describing intended behavior rather than freshly re-verified behavior, the gap count above (G1–G15) may be understated. Recommend a 30-minute spot-check of the specific line references cited in Part 1 before this plan is finalized as a work order.
4. A sequencing risk the plan doesn&apos;t mention: storage durability
The code samples in Workstream 1 write directly to a DB.auditLog array (DB.auditLog.unshift(entry)), and Workstream 7 stores evidence as base64 strings in memory, explicitly flagged in the plan itself as “for dev; production → S3/blob.” This is consistent with the rest of the codebase running on an in-process object rather than a persisted, tenant-isolated database — the PostgreSQL + Row-Level Security migration is tracked separately on the broader roadmap and has not landed yet.
Building an elaborate audit trail, version history, and locking system on non-persistent, non-tenant-isolated storage means a meaningful share of this work (schema design, snapshot logic, lock semantics) will need to be re-validated — and in places rewritten — once the Postgres/RLS migration happens. Two honest options:
Option A (recommended): Pull the Postgres + RLS migration forward to run immediately before or alongside WS1, so the audit/snapshot/lock tables are built on real, durable, tenant-isolated storage the first time.
Option B: Proceed with WS1–WS8 on the current in-memory model as an explicitly-labeled prototype/demo milestone, with a known, budgeted re-implementation pass once Postgres lands. This is only acceptable if the client-facing SOC 2/ISO 27001 claims are not made against this milestone.
Whichever option is chosen, it should be a stated decision in the roadmap, not a silent assumption — this is exactly the kind of gap that turns into a client-facing surprise later.
5. Answers to the plan&apos;s open questions
Q1 — Risk appetite/tolerance configuration: Yes, but sequence it after WS1–WS4 land, not alongside. Appetite-breach detection is only meaningful once risk scores and statuses are trustworthy (audited, versioned, lifecycle-enforced) — building it earlier means re-testing it against a moving target.
Q2 — Risk categories/taxonomy: Yes, and it&apos;s small enough to fold into WS3 (Lifecycle) rather than run as a separate workstream — categoryId already exists as a field, this is primarily a reference-data + admin-UI task, estimated at 8-10 additional hours inside WS3.
Q3 — Notifications: Defer. It&apos;s a reasonable feature but has zero dependency on WS1-WS8 functioning correctly first, and adding email infrastructure mid-stream increases the surface area of this already-large change set. Revisit after Phase 5 (Part 6) closes.
Q4 — Sequential vs. parallel: Neither, exactly as scoped. Critical path first (WS2 → WS1 → WS3 → WS4) is correct and should stay strictly sequential — these all touch server.ts and DataContext.tsx and a parallel effort here is a merge-conflict and regression risk, not a time saver. WS6/WS7/WS8 (Phase 4) can genuinely run in parallel since they touch mostly-disjoint code paths, but only after the Section 4 storage-durability decision above is made — building the lock/evidence/import logic twice would be wasted effort.

Part 4 — Detailed Implementation Workstreams
Workstream 1: Universal Audit Trail (Gaps G1, G2)
SOC 2 CC7.2/CC8.1 · ISO 27001 A.5.28 · COSO ERM Information & Reporting
Principle: every mutation to any entity in the system — risk, control, treatment, asset, KRI, user, document — creates an immutable audit record. This is the single most important gap to close.
What gets audited
Who: user ID, name, role at time of action
What: entity type, entity ID, action type, field-by-field changes (old value → new value)
When: ISO 8601 timestamp, server-generated, not client-supplied
Where: IP address, user agent (from request headers)
Why: optional note, mandatory for approval/rejection/closure actions
Data model addition to server.ts DB
auditLog: {
  id, entityType: &apos;risk&apos;|&apos;control&apos;|&apos;treatment&apos;|&apos;asset&apos;|&apos;kri&apos;|&apos;document&apos;|&apos;user&apos;|&apos;mapping&apos;,
  entityId, entityCode?, action: &apos;create&apos;|&apos;update&apos;|&apos;delete&apos;|&apos;approve&apos;|&apos;reject&apos;|

Workstream 2: RBAC Role Hierarchy (Gap G5)
SOC 2 Logical Access · ISO 27001 A.5.15/A.8.3
Current problem
RBAC is enforced via scattered if-checks in server.ts, repeated roughly 12 times with slight variations — easy to forget on new endpoints, not centralized (a missed check is a security hole), and not granular enough to express “Risk Owner can edit own risks but not others.”
Solution: centralized permission middleware

};

export const ROLE_PERMISSIONS: Record<Role, Permission[]> = { /* full matrix, see Part 3.2 */ };
 
const requirePermission = (...permissions) => (req, res, next) => {
  const userPermissions = ROLE_PERMISSIONS[req.user?.role] || [];
  if (!permissions.some(p => userPermissions.includes(p))) {
    createAuditEntry(&apos;system&apos;, &apos;access_denied&apos;, undefined, &apos;access_denied&apos;, req.user, null, null, req);
    return res.status(403).json({ error: `Your role does not have permission for this action.` });
  }
  next();
};
 
app.post(&quot;/api/v1/risks&quot;, authenticateToken, requirePermission(&apos;risk:create&apos;), handler);

export function usePermissions() {
  const { currentRole } = useData();
  const can = (permission: Permission) => ROLE_PERMISSIONS[currentRole]?.includes(permission) ?? false;
  return { can, currentRole };
}

Workstream 4: Approval Workflow Engine (Gap G3)
SOC 2 CC8.1 · ISO 27001 A.5.1
New risks start as Draft — editable freely
Submitted risks (Pending Review) get a reviewer assigned based on severity tier
At approval stage, minimum approver is determined by score: Critical (>80) → CRO/Admin; High (51–80) → Compliance+; Moderate (21–50) → Risk Owner+; Low (≤20) → any authorized role
Editing an Accepted risk stages changes in pendingChanges and moves the risk to Pending Approval; the original stays visible until approved
Approval merges pendingChanges, creates a snapshot and audit entry; rejection clears pendingChanges and requires a reason

Workstream 6: Concurrent Edit Control (Gap G6)
Mechanism: optimistic locking + edit sessions.
risk.version = 1  // increments on every save
 
POST /api/v1/locks { entityType: &quot;risk&quot;, entityId: &quot;r1&quot; }
// -> { lockId, expiresAt (5 min), heldBy: { userId, name } }
 
PUT /api/v1/risks/:id   Headers: { &quot;If-Match&quot;: &quot;3&quot; }
// Server: is this user the lock holder (or expired)? does version match?
// mismatch -> 409 Conflict, response includes current record to merge against
Frontend: acquire lock + “Editing…” indicator on edit mode; banner if another user holds the lock; re-acquire warning if the lock expires mid-edit; conflict modal on version mismatch; auto-release on navigate-away.

End-to-End Scenario: Full Risk Lifecycle
1. Risk Owner logs in, creates risk “Data Center Fire” → status: Draft, audit entry created
2. Risk Owner submits for review → status: Pending Review, audit entry
3. Compliance Officer reviews, assigns scores (Likelihood=4, Impact=5) → status: Assessed
4. System computes IRS = 60 (High) → requires CRO approval for acceptance
5. Risk Owner creates treatment plan “Install fire suppression” → linked to risk
6. Status: Treatment Planning → In Treatment as work progresses
7. Treatment reaches 100% → Compliance Officer reviews → status: Under Review
8. CRO/Executive approves → status: Accepted, audit entry with approval note
9. 90 days later, periodic review triggered → status: Monitoring → Under Review
10. If risk no longer relevant → CRO closes → status: Closed, mandatory note
At every step: audit entry created, snapshot saved, timestamps recorded, permissions enforced.
